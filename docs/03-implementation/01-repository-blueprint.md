# وصف الهيكل المستقبلي وقواعد التطوير

NSC-REP-01 | وصف فقط | 2026-11-09.

## البنية الحالية

docs للتحليل والتصميم، project-meta لضبط الوثائق، prompts لمراجعتها. الوثائق الأصلية الخمس محفوظة في الجذر. لا توجد حاجة لإنشاء ملفات تطبيق وهمية لإظهار اكتمال البنية.

## البنية المستقبلية المقترحة

- platform/backend: واجهات API وحالات الاستخدام والمجال ومحولات البنية التحتية؛ لكل وحدة في [المعمارية](../02-design/01-architecture.md) حدودها واختباراتها لاحقًا.
- platform/frontend: واجهة المستفيد وواجهة الفني والإدارة؛ features بحسب مجال العمل، ومكونات مشتركة للعرض فقط.
- platform/worker: معالجة الأحداث والتوقيت والاستيراد؛ يستدعي حالات الاستخدام ولا ينسخ منطقها.
- platform/mobile: عميل هاتف مؤجل؛ لا يملك الحقيقة التشغيلية أو حساب SLA.
- contracts: مصدر واحد لعقد REST وعقود الأحداث مستقبلًا. الآن مرجعه [كتالوج API](../09-api/01-api-catalog.md)، وليس ملف OpenAPI مكتملًا.
- design-system: تعريفات موحدة للألوان والمسافات والخطوط والمكونات مستقبلًا، دون نسخة مستقلة لكل تطبيق.
- infrastructure وdeployment: أوصاف البيئات والتسليم والنسخ الاحتياطي عند التصريح بالتنفيذ.
- tests: سيناريوهات وحدات وتكامل وعقود وعزل وأداء؛ وجود هذا الوصف لا يعني إنشاء اختبارات.

لا تُنشأ هذه المجلدات البرمجية ضمن الحزمة الحالية. بادئة الوحدات المقترحة nsc_ والخدمات nsc- والحزم @nexusservice/؛ لا تعتمد nxa_ أو نطاق nexusasset.cloud. أسماء النطاقات العامة للمنتج لم تحجز ولم تعتمد.

## ضوابط منطقية

لا يكتب الطلب في جدول أصل مباشرة، بل يستدعي حجزًا أو تسليمًا في وحدة الأصول. لا يحول Serializer أو مكون واجهة نفسه إلى محرك موافقة. التحقق الشكلي عند حدود الإدخال، وقاعدة العمل داخل المجال، والتفويض في حالة الاستخدام، وسلامة الربط في التخزين أيضًا.

كل تعديل مهم يحدد الأثر على المتطلب والعقد والتدقيق والاختبارات. الأخطاء المتوقعة لها رمز وشرح آمن؛ الأخطاء الداخلية لا تعرض أثر المكدس. الإلغاء لا يعني حذفًا، والعمليات المالية أو المخزنية تستخدم تعويضًا موثقًا بعد الحفظ.

## جاهزية البدء مستقبلًا

قبل اختيار الإصدارات يلزم اعتماد Q-01 إلى Q-07 وتحديد حدود P1 وعقودها. قبل التطوير يلزم تكليف منفصل؛ هذه الوثيقة ليست تعليمات لبدء تثبيت حزم أو توليد كود.
