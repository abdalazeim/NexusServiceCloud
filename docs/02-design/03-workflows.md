# دورات العمل والموافقات والأتمتة

NSC-WF-01 | مقترح | 2026-11-09.

## طلب الخدمة والحادث

الحالات المشتركة: Open، InProgress، PendingRequester، PendingExternal، Resolved، Closed، Cancelled. WaitingApproval وRejected تخص طلبات الخدمة التي تتطلب موافقة. لا يفترض أن كل Pending يوقف SLA؛ سياسة المؤشر هي المرجع.

- Open → InProgress: فني مؤهل أو تعيين آلي مع مجموعة مسؤولة؛ يسجل الفاعل ولا يعد التعيين ردًا للمستفيد.
- Open → WaitingApproval: طلب كتالوج يحتاج موافقة؛ تحفظ نسخة الطلب والسياسة.
- WaitingApproval → Open: اكتمال النصاب؛ يعود لطابور التنفيذ. الرفض ينقله Rejected مع سبب. لا ينفذ قبل الموافقة.
- InProgress → PendingRequester: سؤال عام محدد للمستفيد مع سبب انتظار؛ لا يكفي تعليق داخلي.
- InProgress → PendingExternal: مرجع اعتماد خارجي ومالك متابعة وموعد مراجعة.
- PendingRequester/PendingExternal → InProgress: وصول الاستجابة المطلوبة أو انتهاء سبب التعليق؛ يحتفظ بمقاطع الوقت.
- InProgress → Resolved: ملخص حل ورمز نتيجة وحقول الإغلاق المطلوبة. ربط مقال اختياري إلا إذا ألزمه النموذج.
- Resolved → Closed: تأكيد المستفيد أو سياسة إغلاق تلقائي معلنة. خط الأساس المقترح لا يغلق تلقائيًا قبل اعتماد مدة الانتظار.
- Resolved/Closed → InProgress: إعادة فتح بسبب موثق وصلاحية مناسبة؛ يبدأ مقطع حل جديد ضمن الميزانية المتبقية ولا يمحو التجاوز السابق.
- الحالات غير النهائية → Cancelled: سبب وإذن؛ يلغي المهام غير المنفذة والحجوزات القابلة للإلغاء. تعويض الشراء المستلم مسار مستقل.

الرفض والإلغاء نتيجتان منفصلتان عن الحل، وتعرضان مستقلتين في التقارير. الانتقالات غير المذكورة ممنوعة افتراضيًا؛ توسيعها يحتاج نسخة دورة حياة ومراجعة أثر.

## دورة المشكلة

New → Investigation → KnownError أو SolutionPlanned → Resolved → Closed. يمكن الحل مباشرة من Investigation إذا لم يحتج خطأ معروفًا منشورًا. KnownError يتطلب وصف السبب أو حدود المعرفة والحل المؤقت. الإغلاق يتطلب مراجعة نتيجة العلاج؛ إعادة الفتح تعيد Investigation وتحفظ الاستنتاج السابق.

## دورة التغيير

Draft → Assessment → AwaitingApproval → Scheduled → Implementing → Review → Closed. رفض الموافقة يعطي Rejected، وفشل التنفيذ يعطي Failed ثم قرار موثق: Rollback أو Remediation، وبعدهما Review. لا يُخفى الفشل بتحويله نجاحًا عند اكتمال التراجع.

القياسي: قالب ذو تقييم وموافقة سابقة وحدود واضحة؛ الخروج عن الحدود يحوله لمسار عادي. الطارئ: مسؤول مفوض يصرح بالتنفيذ ويسجل السبب والحد الأدنى من خطة التراجع؛ تظل المراجعة اللاحقة إلزامية. التعارض مع نافذة منع أو CI متأثر ينتج منعًا أو استثناء معتمدًا، لا تجاهلًا صامتًا.

## الموافقات

تثبت قائمة المؤهلين ونسخة المورد عند بدء المراجعة. لكل خطوة نمط all أو quorum مع قيمة صريحة؛ رفض واحد يرفض الخطوة في السياسة الأولية. امتناع أو غياب ليس موافقة. انتهاء المهلة يصعد إلى مسؤول بديل ولا يوافق تلقائيًا. التفويض مؤقت ويحتفظ بالمفوّض والمفوّض إليه.

تعديل التكلفة أو النطاق أو المخاطر يبطل الموافقات السابقة؛ تبقى القرارات كتاريخ وتبدأ نسخة جديدة. تعديل إملائي غير مؤثر يحدد في سياسة الحقول. عزل مقدم الطلب عن الموافق يفرض عندما تتطلب السياسة فصل الواجبات. الأرقام 10 مستويات و10 أشخاص في القالب المرجعي ليست حدودًا معتمدة لهذا التصميم.

## شراء وأصل وإصدار

الشراء: Draft → Submitted → Approved → Sent → PartiallyReceived → Received → Closed، مع Rejected/Cancelled حيث لا يناقض الاستلام. لا يصبح الأصل مسندًا بمجرد استلامه؛ يضاف إلى المخزن ثم يسلم بعهدة.

الأصل: InStock → Reserved → Assigned → Maintenance → InStock أو Assigned، ثم Retired → Disposed. إخراج أصل من الخدمة يعالج الحجوزات المفتوحة ويوثق إزالة البيانات إن كانت مطلوبة. العهدة السابقة لا تختفي.

الإصدار: Planned → Ready → Deploying → Verification → Released، أو Failed ثم Rollback/Remediation. اكتمال مهام المشروع لا يكفي للانتقال Ready دون أدلة التغيير والقبول.

## قواعد الأتمتة

القاعدة = حدث + شروط + ترتيب + أفعال مسموحة + نسخة + نطاق مؤسسة/مكتب. التصميم الأولي يدعم التعيين والتنبيه وتحديث حقول مسموحة وإنشاء مهمة؛ لا يدعم تنفيذ نص برمجي حر.

تختبر القاعدة على أمثلة قبل التفعيل وتعرض «لماذا انطبقت». تسجل operation_id وcausation_id، وتمنع إعادة فعل القاعدة على الحدث نفسه. حد عمق مقترح 10 أحداث سببية يوقف الحلقة ويولد تنبيهًا؛ يعتمد بعد مراجعة حالات العمل. القواعد الجوهرية كالصلاحيات وسلامة الانتقالات لا يمكن لقاعدة أتمتة تجاوزها.
