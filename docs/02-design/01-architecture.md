# المعمارية المقترحة وحدود المسؤوليات

NSC-ARCH-01 | مقترح وليس وصف تنفيذ | 2026-11-09.

## النمط العام

تطبيق خلفي موحد مقسم إلى وحدات أعمال مستقلة منطقيًا (Modular Monolith)، وواجهة ويب، وعمليات خلفية. يسمح ذلك بمعاملة موثوقة لدورة الطلب ويحد من كلفة الخدمات الموزعة في البداية. الفصل إلى خدمات مستقلة قرار لاحق تدعمه قياسات الحمل أو حدود فريق العمل، لا عدد الوحدات.

المسار: قناة المستخدم ← بوابة اتصال آمن ← واجهة ويب/BFF أو API ← حالة استخدام ← مجال الأعمال ← منافذ تخزين أو تكامل. عامل خلفي يعالج الإشعارات والمواعيد والأحداث الموثوقة. قاعدة البيانات تحفظ الحقيقة التشغيلية، والمرفقات في مخزن مستقل، والذاكرة المؤقتة ليست مرجعًا للحالة.

## وحدات المجال وأسماء مقترحة

- nsc_identity: الهوية والجلسات والعضويات والتفويض. لا يقرر انتقال حالة الطلب.
- nsc_tenants: المؤسسة والمواقع والأقسام ومكاتب الخدمة. لا تختزل المؤسسة إلى نطاق بريد.
- nsc_catalog: الخدمات وعناصر الكتالوج والنماذج المنشورة والجمهور.
- nsc_requests: الطلبات والحوادث والتعليقات والتعيين وسجل الحالة؛ يملك أصل الطلب.
- nsc_service_levels: نسخ SLA والتقاويم ومقاطع القياس والتصعيد وOLA؛ يستهلك أحداث الطلب ولا يملك نصه.
- nsc_automation: قواعد وشروط وأفعال مسموحة وسجل تشغيل؛ يطلب الأفعال عبر حالات الاستخدام نفسها.
- nsc_approvals: تعريف سياسة الموافقة وحالاتها وقرارات الأفراد والتفويض.
- nsc_problems: السبب الجذري والخطأ المعروف والروابط مع الحوادث.
- nsc_changes: RFC والمخاطر وخطط التنفيذ والتراجع وجدولة التغيير.
- nsc_delivery: المشاريع والمهام والتبعيات والإصدارات وعمليات النشر المسجلة.
- nsc_assets: ملكية الأصل وعهدته وحركته وتقاعده وحجوزاته وصيانته.
- nsc_cmdb: عناصر التكوين وعلاقات الاعتماد وخرائط الأثر؛ الأصل المادي وCI مفهومان مختلفان.
- nsc_procurement: الشراء والاستلام والمورد والعقد؛ لا ينفذ دفترًا محاسبيًا.
- nsc_knowledge: المقالات ونسخها ومراجعتها وجمهورها.
- nsc_integrations: البريد والمراقبة والاكتشاف والموصلات وخرائط حقولها.
- nsc_insights: تقارير وقراءات مشتقة واستبيانات، مع إعلان وقت تحديثها.
- nsc_audit وnsc_notifications: التدقيق والتسليم، دون تغيير قرار الأعمال الأصلي.
- nsc_ai: اقتراحات خاضعة للصلاحيات والمراجعة، قابلة للتعطيل بالكامل.

## اتجاه الاعتماد

واجهة التسليم تستدعي التطبيق، والتطبيق يستخدم المجال ومنافذ معلنة. البنية التحتية تحقق منافذ التخزين والهوية والبريد. المجال لا يعرف HTTP أو قواعد البيانات أو مزود AI. المشاركة بين الوحدات تقتصر على معرفات وقيم مستقرة وعقود صريحة، لا نموذج موحد ضخم.

تحديث الطلب وتاريخ حالته وحدثه وتدقيق نجاحه معاملة واحدة. حجز أصل يحتاج معاملة في وحدة الأصول قبل تأكيد تخصيصه. معالجة مهمة شراء طويلة عبر حالات واضحة وتعويض، ولا نُبقي معاملة قاعدة بيانات مفتوحة أثناء اتصال خارجي.

## Web وBFF

الواجهة تعرض النماذج وحالة العمليات، وBFF يجمع قراءات الشاشة ويحمي جلسة الويب إن اختير. قرار التفويض النهائي في الخادم لكل عملية وكل كائن. الهاتف والعملاء الخارجيون يستخدمون العقد نفسه بصلاحيات مستقلة؛ لا ينسخون محرك SLA أو الموافقات.

## التقنية المرشحة

Django/DRF وPostgreSQL للمنطق والتخزين، Next.js/React للويب، وعامل مهام مع طابور ورسائل موثوقة، ومخزن ملفات خاص. هذه عائلات تقنيات مستلهمة من المرجع، لا قرار شراء أو تثبيت. اختيار Redis/Celery أو وسيط آخر، ونسخ الحزم، وتقنية الهاتف والبنية التشغيلية تُحسم في ADR ومصفوفة توافق لاحقًا. لا تُنقل أرقام الإصدارات المتعارضة في مراجع NexusAsset.

## التوسع

تبدأ التقارير بقراءات مقيّدة وفهارس مناسبة؛ لاحقًا تنشأ إسقاطات مشتقة لا تتجاوز صلاحيات المصدر. تفصل طوابير الإشعار عن استيراد الأصول حتى لا يؤخر استيراد كبير تصعيدًا. يطبق حد استخدام لكل مؤسسة مع أولوية عادلة. نموذج العزل موضح في [الأمن](../07-security/01-security-tenancy.md).
