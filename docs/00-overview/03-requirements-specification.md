## 1. ملخص تنفيذي

تحدد هذه الوثيقة **المتطلبات الوظيفية** (Functional Requirements) و**المتطلبات غير الوظيفية** (Non-Functional Requirements) لمنصة NexusServiceCloud باستخدام **ترميز EARS** (Easy Approach to Requirements Syntax) لضمان الوضوح والقابلية للاختبار. كل متطلب مرتبط بـ **معايير قبول** (Acceptance Criteria) قابلة للاختبار الآلي، وبـ **حالات استخدام** (DOC-02)، و**حالات اختبار** (DOC-10).

## 2. اصطلاحات الترميز (Notation Conventions)

### 2.1 ترميز EARS

| النمط | القالب | مثال |
|-------|--------|-------|
| **شائع (Ubiquitous)** | النظام **يجب أن** \<فعل\> | النظام يجب أن يسجل طلبًا جديدًا |
| **مبني على حدث (Event-Driven)** | **عند** \<حدث\>، النظام **يجب أن** \<فعل\> | عند استقبال بريد، النظام يجب أن ينشئ/يسترجع طلبًا |
| **حالة (State-Driven)** | **طالما** \<حالة\>، النظام **يجب أن** \<فعل\> | طالما الطلب في حالة "جديد"، النظام يجب أن يسمح بالتعيين |
| **ميزة اختيارية (Optional Feature)** | **حيث** \<شرط\>، النظام **يجب أن** \<فعل\> | حيث ميزة AI مفعلة، النظام يجب أن يقترح تصنيفًا |
| **قيود (Unwanted Behavior)** | النظام **يجب ألا** \<فعل\> | النظام يجب ألا يسمح بطلب عنصر مخفي عبر API |

### 2.2 أولويات المتطلبات

| الرمز | المعنى | الوصف |
|------|--------|--------|
| **P1** | أساسي للخط الأساسي | يجب تسليمه في P1 (MVP) |
| **P2** | تحكم تشغيلي | يسلم في P2 |
| **P3** | دورة موارد | يسلم في P3 |
| **P4** | توسع/تحسين | يسلم في P4 أو لاحقًا |

### 3.2 تفصيل المتطلبات الوظيفية مع EARS ومعايير القبول

#### REQ-FN-001: المؤسسات والهيكل التنظيمي (P1)

**EARS:**
- **REQ-FN-001.1** (شائع): النظام **يجب أن** يدعم إنشاء مؤسسة مع اسم، حالة، نمط نشر، منطقة زمنية افتراضية.
- **REQ-FN-001.2** (شائع): النظام **يجب أن** يدعم مواقع، أقسام، مكاتب خدمة، مجموعات عمل تابعة لمؤسسة.
- **REQ-FN-001.3** (حالة): **طالما** المؤسسة نشطة، النظام **يجب أن** يسمح بإدارة عضويات المستخدمين وأدوارهم.
- **REQ-FN-001.4** (شائع): النظام **يجب أن** يدعم تقويم عمل لكل مؤسسة/موقع يستخدم في حسابات SLA.
- **REQ-FN-001.5** (قيود): النظام **يجب ألا** يسمح لمدير مؤسسة (أ) باسترجاع قسم أو مستخدم تابع لمؤسسة (ب).

**معايير القبول:**
| AC | الوصف | اختبار |
|----|--------|--------|
| **AC-001** | مدير مؤسسة (أ) لا يسترجع قسمًا أو مستخدمًا تابعًا لمؤسسة (ب) | تكامل: استعلام API لمؤسسة (أ) يعيد 403/404 لموارد (ب) |
| **AC-002** | تعطيل موقع لا يحذف تاريخه من الطلبات | تكامل: طلبات مرتبطة بموقع معطل تظل قابلة للقراءة مع إشارة "معطل" |

---

#### REQ-FN-002: الهوية والتفويض (P1)

**EARS:**
- **REQ-FN-002.1** (حدث): **عند** مصادقة مستخدم عبر مزود هوية (OIDC/SAML)، النظام **يجب أن** ينشئ/يحدث عضوية في المؤسسة المستهدفة مع أدوار افتراضية.
- **REQ-FN-002.2** (شائع): النظام **يجب أن** يطبق نموذج RBAC/ABAC مع أفعال، أنواع موارد، نطاقات (مؤسسة، موقع، قسم، مجموعة، ملكية سجل).
- **REQ-FN-002.3** (حدث): **عند** إيقاف عضوية مستخدم، النظام **يجب أن** يبطل جميع جلساته النشطة ويرفض العمليات اللاحقة عند إعادة التحقق.
- **REQ-FN-002.4** (حالة): **طالما** المستخدم في مجموعة دعم مؤهلة، النظام **يجب أن** يسمح بتعيين الطلبات له.
- **REQ-FN-002.5** (قيود): النظام **يجب ألا** يسمح لفني خارج مجموعة الطلب بتغييره.

**معايير القبول:**
| AC | الوصف | اختبار |
|----|--------|--------|
| **AC-003** | فني خارج مجموعة الطلب يُمنع من تغييره (403) | وحدة: استدعاء UC-APP-REQS-003 بصلاحية ناقصة → 403 |
| **AC-004** | مستخدم موقوف لا يكمل عملية قائمة بعد إعادة التحقق | تكامل: إيقاف عضوية → طلب لاحق بـ Access Token صالح → 401 |
| **AC-005** | SCIM يوفر/يلغي مستخدمين بأدوار/مجموعات صحيحة | عقد: تحميل SCIM payload → عضوية مطابقة في DB |

#### REQ-FN-003: الحوادث (P1)

**EARS:**
- **REQ-FN-003.1** (حدث): **عند** تسجيل حادث من البوابة أو يدويًا لمكالمة/بريد، النظام **يجب أن** ينشئ طلبًا بنوع `incident`، رقم مرجعي فريد داخل المؤسسة، نوع ثابت، أولوية، خدمة.
- **REQ-FN-003.2** (حدث): **عند** استقبال نفس الرسالة (Message-ID مكرر)، النظام **يجب أن** يعيد المرجع الموجود ولا ينشئ طلبًا جديدًا.
- **REQ-FN-003.3** (حالة): **حيث** محتوى ناقص (حقول إلزامية)، النظام **يجب أن** ينقل الطلب إلى طابور فرز واضح مع أسباب الناقص ولا يفقد البيانات.
- **REQ-FN-003.4** (شائع): النظام **يجب أن** يدعم إجراء تحويل نوع موثق (Incident ↔ Service Request) مع إعادة تحقق للسياسات.
- **REQ-FN-003.5** (قيود): النظام **يجب ألا** ينشئ حادثًا آخر لبريد مكرر.

**معايير القبول:**
| AC | الوصف | اختبار |
|----|--------|--------|
| **AC-006** | إعادة تسليم نفس الرسالة تعيد المرجع الموجود | تكامل: POST بريد مكرر → استجابة 200 مع request_id نفسه |
| **AC-007** | محتوى ناقص → طابور فرز مع أسباب، لا فقدان بيانات | وحدة: إنشاء طلب بحقول ناقصة → state="triaged"، validation_errors غير فارغ |
| **AC-008** | تحويل نوع موثق مع إعادة تحقق SLA/تعيين | تكامل: تحويل Incident→ServiceRequest → SLA instance معاد حسابه |

#### REQ-FN-004: كتالوج وطلبات الخدمة (P1)

**EARS:**
- **REQ-FN-004.1** (شائع): النظام **يجب أن** يدعم خدمات، عناصر كتالوج تتبع خدمة، جمهور مستهدف، نماذج ذات إصدارات (FormVersion)، سياسة موافقة لكل عنصر.
- **REQ-FN-004.2** (حدث): **عند** طلب مستفيد لعنصر كتالوج، النظام **يجب أن** يسجل استخدامًا، مركز تكلفة، ويرسل للموافقة وفق السياسة.
- **REQ-FN-004.3** (حالة): **طالما** الطلب جارٍ، النظام **يجب أن** يحتفظ بنسخة النموذج (FormVersion) المستخدمة رغم نشر نسخة جديدة.
- **REQ-FN-004.4** (قيود): النظام **يجب ألا** يسمح للمستخدم بطلب عنصر مخفي عبر API مباشر.
- **REQ-FN-004.5** (شائع): النظام **يجب أن** يدعم حجز مخزون، وإن لم يتوفر → إنشاء احتياج شراء مرتبط.

**معايير القبول:**
| AC | الوصف | اختبار |
|----|--------|--------|
| **AC-009** | لا يقدم مستخدم عنصرًا مخفيًا عبر API (403/404) | تكامل: POST /requests بعنصر audience لا يشمل المستخدم → 403 |
| **AC-010** | الطلب الجاري يحتفظ بنسخة النموذج رغم نشر نسخة جديدة | تكامل: إنشاء طلب → نشر FormVersion جديدة → الطلب يشير للقديمة |
| **AC-011** | حجز مخزون/إنشاء احتياج شراء عند عدم توفر | تكامل: طلب عنصر بمخزون 0 → PurchaseNeed مرتبط ينشأ تلقائيًا |

#### REQ-FN-005: التصنيف والتعيين (P1)

**EARS:**
- **REQ-FN-005.1** (شائع): النظام **يجب أن** يدعم تسلسل Category → Subcategory → Item مع تعطيل يمنع اختيار جديد ويحفظ التاريخ.
- **REQ-FN-005.2** (شائع): النظام **يجب أن** يدعم قواعد تعيين مرتبة (مجموعة، فني، مهارات، حمل عمل، نوبة).
- **REQ-FN-005.3** (حدث): **عند** غياب فني مؤهل، النظام **يجب أن** يسند الطلب إلى طابور المجموعة دون فقد الملكية (group_id يظل مضبوطًا).
- **REQ-FN-005.4** (قيود): النظام **يجب ألا** يقبل عنصر تصنيف خارج فئته الفرعية الأبوية.

**معايير القبول:**
| AC | الوصف | اختبار |
|----|--------|--------|
| **AC-012** | لا يقبل عنصر خارج فئته الفرعية (تحقق سلامة هرمية) | وحدة: تعيين Item لا ينتمي لـ Subcategory → validation error |
| **AC-013** | تكرار قواعد متطابقة يحسم بترتيب صريح؛ غياب فني → طابور المجموعة | تكامل: قاعدتان متطابقتان → الأسبق تفوز؛ لا فني مؤهل → group_id مضبوط، technician_id فارغ |

#### REQ-FN-006: تعاون الفريق (P1)

**EARS:**
- **REQ-FN-006.1** (شائع): النظام **يجب أن** يدعم تعليقات عامة (مرئية للمستفيد)، ملاحظات داخلية (فريق فقط)، مرفقات، سجل وقت، متابعين.
- **REQ-FN-006.2** (قيود): النظام **يجب ألا** تصل ملاحظة داخلية إلى المستفيد عبر الشاشة أو البريد أو التصدير.
- **REQ-FN-006.3** (شائع): النظام **يجب أن** يعزل المرفقات للفحص (ملفات مشبوهة) ويمنع تنزيلها حتى اجتياز الفحص.
- **REQ-FN-006.4** (شائع): النظام **يجب أن** يحفظ التصحيح في سجل الوقت كتعديل مدقق (audited modification).

**معايير القبول:**
| AC | الوصف | اختبار |
|----|--------|--------|
| **AC-014** | ملاحظة داخلية لا تظهر في استجابة API للمستفيد | وحدة: GET /requests/{id}/comments كمستفيد → فقط visibility=public |
| **AC-015** | مرفق معزول للفحص يعيد 403 عند محاولة تنزيل قبل اجتياز | تكامل: رفع ملف → حالة "quarantined" → تنزيل → 403 |
| **AC-016** | تصحيح سجل وقت يسجل كـ AuditEvent مع قبل/بعد | وحدة: PATCH /worklogs/{id} → AuditEvent يسجل القيم القديمة والجديدة |

#### REQ-FN-007: دورة حياة الطلب (P1)

**EARS:**
- **REQ-FN-007.1** (حالة): **طالما** الطلب في حالة قابلة للانتقال، النظام **يجب أن** يفرض انتقالات محكومة بصلاحية، حقول مطلوبة، نسخة سجل متوقعة (Optimistic Concurrency).
- **REQ-FN-007.2** (قيود): النظام **يجب ألا** يسمح بالإغلاق بدون ملخص حل.
- **REQ-FN-007.3** (حدث): **عند** تحديث متزامن من فنيين، النظام **يجب أن** يرفض التحديث المتعارض (409) بدل الكتابة فوق.
- **REQ-FN-007.4** (شائع): النظام **يجب أن** يحفظ تاريخ إعادة الفتح مع سبب وفاعل.

**معايير القبول:**
| AC | الوصف | اختبار |
|----|--------|--------|
| **AC-017** | رفض إغلاق بلا ملخص حل (validation error) | وحدة: انتقال إلى "closed" بدون resolution_summary → 422 |
| **AC-018** | رفض تحديث متعارض (409) مع نسخة سجل غير مطابقة | تكامل: طلبان PATCH متزامنان → أحدهما 200، الآخر 409 |
| **AC-019** | تاريخ إعادة الفتح يسجل مع سبب، فاعل، وقت | وحدة: انتقال من "closed" إلى "reopened" → RequestTransition مع reason |

#### REQ-FN-008: SLA والتصعيد (P1/P2)

**EARS:**
- **REQ-FN-008.1** (شائع): النظام **يجب أن** يدعم زمن استجابة وحل مستقلين، تقاويم عمل، قواعد إيقاف (pause)، تصعيد مرحلي، وميزانيات OLA للفرق الداخلية.
- **REQ-FN-008.2** (حدث): **عند** إنشاء طلب مع SLA مطبق، النظام **يجب أن** يثبت نسخة سياسة SLA والتقويم ويبدأ قياس الوقت (SLAInstance مع أهداف مطلقة).
- **REQ-FN-008.3** (حالة): **طالما** مقطع ساعة نشط، النظام **يجب أن** يراقب استجابة/حل باستمرار.
- **REQ-FN-008.4** (حدث): **عند** تجاوز عتبة تصعيد، النظام **يجب أن** ينفذ إجراء تصعيد (إشعار، إعادة إسناد، ترقية أولوية) ويسجل EscalationExecution فريد (مفتاح فريد يمنع التكرار).
- **REQ-FN-008.5** (حدث): **عند** إعادة فتح طلب، النظام **يجب أن** يعيد حساب SLA Instance مع أهداف محدثة ولا يعيد تصعيدًا منفذًا مسبقًا.
- **REQ-FN-008.6** (شائع): النظام **يجب أن** يدعم OLA: كل إعادة إسناد تبدأ مقطعًا جديدًا (OLASegment) مع ميزانية متفق عليها ولا تمحو السابق.

**معايير القبول:**
| AC | الوصف | اختبار |
|----|--------|--------|
| **AC-020** | سيناريو عطلة/إيقاف/إعادة فتح يعطي أرقام SLA محددة | تكامل: طلب عبر عطلة مع pause_rule → استجابة/حل محسوبة صحيحة |
| **AC-021** | لا يتكرر تصعيد واحد عند إعادة معالجة الحدث (EscalationExecution فريد) | وحدة: تشغيل محرك تصعيد مرتين للحدث نفسه → تنفيذ واحد مسجل |
| **AC-022** | OLA: إعادة إسناد تبدأ مقطعًا جديدًا مع ميزانية، السابق محفوظ | تكامل: إعادة إسناد طلب → OLASegment جديد، السابق بوقت خروج مضبوط |

#### REQ-FN-009: الموافقات (P1 بسيط، P2 متقدم)

| **REQ-NFR-DC-005** | النظام **يجب أن** يشفر البيانات الحساسة في الراحة (AES-256) والنقل (TLS 1.3) مع مفاتيح تديرها المؤسسة (CMK/CMK per tenant اختياري) | صفر بيانات حساسة غير مشفرة | مسح تشفير، تدقيق مفاتيح | P1 |
