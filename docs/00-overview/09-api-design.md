## 1. ملخص تنفيذي

تحدد هذه الوثيقة العقد المفاهيمي لواجهات برمجة NexusServiceCloud. تعتمد المنصة على **REST over HTTPS** مع بادئة `/api/v1`، وتستخدم ترقيم cursor، ومعرفاتملية غير قابلة للتكرار (Idempotency Keys)، وإصدار متفائل (optimistic versioning) للكتابة الحساسة. لا يوجد OpenAPI مكتمل أو نقاط نهاية منفذة في هذه المرحلة.

---

## 2. قواعد العقد العام (General Contract Rules)

### 2.1 بادئة وإصدار

- بادئة مقترحة: `/api/v1`
- المؤسسة تُستمد من سياق عضوية موثوق، لا حقل قابل لتغيير الملكية في الطلب.

### 2.2 الاستعلام والقوائم

- قائمة موارد بترقيم **cursor** وحد 50 افتراضي و 100 أقصى مقترح.
- ترتيب ثابت مع المعرف لفصل القيم المتساوية.
- مرشحات مسموحة صراحة لكل مورد؛ الأوقات بتنسيق UTC موحد (ISO 8601).

### 2.3 الاستجابة/error

- الأخطاء تحتوي على: `code` ورسالة آمنة و `field_errors` عند الحاجة و `correlation_id`.
- **401** لغياب الهوية.
- **403** لمنع فعل ظاهر.
- **404** للكائن المفقود أو غير المرئي دون كشف وجوده.
- **409** لتعارض حالة/نسخة/مفتاح عملية.
- **422** لمدخلات غير صالحة.
- **429** لتجاوز حد المعدل.
- يجب توحيد هذا الاختيار في العقد الآلي لاحقًا.

### 2.4 الكتابة الحساسة ونسخة متفائلة

- الكتابة الحساسة تستخدم `expected_version`؛ عدم إرساله في تحديث يتطلبه العقد يرفض.
- اختلاف النسخة يعطي **409** مع طلب إعادة القراءة.

### 2.5 명령 غير قابلة للتكرار (Idempotency)

- الإنشاء والأوامر القابلة لإعادة المحاولة تستخدم رأس `Idempotency-Key` مرتبطًا بالمؤسسة والفاعل والعملية وبصمة الحمولة.
- نفس المفتاح والحمولة يعيدان النتيجة الأصلية.
- نفس المفتاح بحمولة مختلفة يرفض.
- مدة حفظ المفاتيح المقترحة 7 أيام.
- أحداث الاستلام والتكامل تملك قيد منع تكرار دائمًا ضمن فترة احتفاظها.

## 3. العمليات الأساسية (Core Operations)

| العملية | النقطة الطرفية | الوصف | FR |
|----------|-------------|--------|-----|
| الهوية والنطاقات | `GET /me`، `GET /memberships` | الهوية والنطاقات المصرح بها دون كشف أعضاء مؤسسة أخرى | FR-01، FR-02 |
| الكتالوج | `GET /catalog/items` | عناصر مرئية فقط | — |
| إنشاء طلب خدمة | `POST /service-requests` | `item_id` و `form_version_id` وقيم النموذج؛ ينتج طلبًا أو أخطاء الحقول | FR-04 |
| قراءة الطلبات | `GET /requests` | ترشيح النوع والحالة والمجموعة والأولوية والمدة ضمن التفويض | FR-03، FR-18 |
| تفاصيل طلب | `GET /requests/{id}` | تفاصيل مرئية وتعليقات حسب الجمهور؛ لا يعيد الملاحظات الداخلية للمستفيد | FR-06 |
| تحديث طلب | `PATCH /requests/{id}` | حقول تحرير مسموحة فقط ونسخة متوقعة | FR-07 |
| انتقال حالة | `POST /requests/{id}/transitions` | `target_status` و `reason` و `resolution` عند اللزوم و `expected_version` | FR-07 |
| إسناد طلب | `POST /requests/{id}/assignments` | `group_id` و `technician_id` والسبب والنسخة | FR-05 |
| إضافة تعليق | `POST /requests/{id}/comments` | النص و `visibility`؛ إذن `internal` للفنيين فقط | FR-06 |
| سجل عمل | `POST /requests/{id}/work-logs` | مدة وزمن ووصف؛ لا يقبل تغيير كاتب السجل خارج التفويض | FR-06 |
| مستوى الخدمة | `GET /requests/{id}/service-level` | السياسة والنسخة والأوقات وحالة الاستجابة والحل | FR-08 |
| قرار موافقة | `POST /approval-instances/{id}/decisions` | `approve/reject` والسبب ونسخة المورد؛ قرار واحد فعال لكل موافق وخطوة | FR-09 |

## 5. الملفات والمهام الطويلة

- رفع المرفق يعطي هوية وحالة `quarantine`؛ لا يصبح قابلًا للربط النهائي والتنزيل قبل فحصه.
- مهمة التقرير أو الاستيراد تعيد `operation_id`؛ القراءة والإلغاء يخضعان لصلاحية صاحب العملية.
- لا يكفي امتلاك رابط النتيجة.
- فشل المهمة يوضح الصفوف المقبولة والمرفوضة ونقطة الاستئناف دون نشر بيانات نطاق آخر.

---

## 6. النمط المعماري لـ API

- **Stateless**: كل طلب يحتوي على كل المعلومات اللازمة للمعالجة.
- **موجه بالموارد**: كل نقطة نهاية تمثل موردًا أو مجموعة موارد.
- **تصميم أولي للعقد**: العقد يُSpec前に الكود، مع مخططات استجابة موحدة.
- **إصدار المسار**: `/api/v1` للإصدارات Hauptية؛ الرؤوس للإصدارات الفرعية عند الحاجة.
